# 채택된 v3.2 운영 계약

채택된 합의 원문의 담당 절을 생략 없이 배포한다. §§21–27.15는 선택적 부록이 아니라 현재 실행 계약이다. 의미 판단은 단일 호스트, 상태·참조·검증은 코어의 책임이다.

## 6. 동적 판단의 공통 표준 — DDC

모든 중요한 동적 판단은 다음 여덟 요소로 정의한다.

| 요소 | 내용 |
|---|---|
| Observable State | 관측 가능한 현재 상태와 근거 |
| Decision Objective | 판단으로 달성하려는 목적 |
| Available Actions | 실행 가능한 대안 |
| Decision Policy | 관측에서 행동을 선택하는 규칙 |
| Constraints | 위반할 수 없는 조건 |
| State Transition | 선택 결과에 따른 상태 변화 |
| Feedback | 실제 결과를 다음 판단에 반영하는 방법 |
| Recovery | 실패·충돌·중단 시 복구 규칙 |

```text
Decision = π(Observed State, Goal, Constraints, Evidence)
```

이는 근거 없는 “AI가 적절히 판단한다”를 허용하지 않는 계약이다.

각 판단 기록에는 선택한 행동, 주요 대안, 관측 근거, 선택 이유, 예상 효과를 간결하게 남긴다. 실행 후에는 실제 효과와 예상과의 차이를 연결한다.

모델의 비공개 내부 사고 과정이나 모든 중간 추론을 저장하는 것을 요구하지 않는다. 중요한 조건의 여덟 구성과 판단 단위·판별 관측의 상세 기준은 §§27.6.2–27.6.6을 함께 적용한다.

### 6.1 관측값 처리

관측값은 다음을 구분한다.

- 직접 측정한 값
- 출처가 있는 외부 주장
- 근거에 기반한 해석
- 아직 확인하지 못한 사항

확인하지 못한 값을 0·실패·낮은 점수로 자동 변환하지 않는다.

정밀한 확률이나 비용 추정에 근거가 없으면 상대적 평가를 사용하며, 그 이유와 불확실성을 기록한다.

## 7. 핵심 추론 모듈

### 7.1 Goal Compiler

**목적:** 사용자의 요청을 관측 가능한 목표·성공 조건·제약으로 변환한다.

**입력:** 사용자 요청, 관련 대화, 기존 프로젝트 정보, 명시적 요구사항.

**출력:** `GoalSpec`.

다음을 구분한다.

- 사용자가 원하는 결과
- 사용자가 명시적으로 요구한 수단
- 사용자가 예시로 제안한 수단
- AI가 추론한 필요 기능
- 실제 확인이 필요한 목표의 모호성

사용자가 특정 수단을 의무로 지정했다면 보존하며 효율성 판단으로 제거하지 않는다. 방법 안내 요청을 수동 수행 선호로 해석하지 않으며, 기능 도출부터 기존 자동화 수단과 조합 가능성을 우선 검토한다. 수동 우선 요구는 원문 근거와 적용 범위를 보존한다 (§§27.7.1–27.7.7).

목표와 성공 조건은 이후 후보 평가와 종료 판단의 기준이 된다. 원문 목적과 의미 단위를 보존하고 누락·자기 축소 여부를 재검토한다. 최초 성공 기준에 없던 중요한 질문도 원문 목표에 연결할 수 있으며, 조언에 필요한 조사를 미래 구현 단계로 미루지 않는다 (§21.2).

사용자에게 추가 지식·기술 판단·학습 깊이·추가 설명을 요구하지 않는다. 기존 맥락·자료와 자율 조사로 해석하며, 없는 선호·권한을 추정하지 않는다. 실제로 해결할 수 없는 조건은 영향을 기록하고 기존 권한 안의 대체 작업과 정확한 결과 범위로 처리한다 (§21.2).

목표 수정이 발생하면 버전을 갱신하고 영향을 받는 판단을 재검토한다. 목표 등록·해석에서 적용 판정 질문을 포함하며, 도구 선택·사용·조합 판단이 필요하면 기존 능력의 충족과 독립적으로 신규 탐색 및 통합 조합 의무를 연결한다 (§§27.8–27.10). 운영 계약의 의무를 사용자 원문 발언으로 위장하지 않는다. 최초 해석은 잠정적이며 원문 결과의 성질·중요 가정·해석 검토 책임을 연결한다. 현재 해석의 지지와 관점 누락 검토를 분리하고, 실제 대조·관측에 따른 변경 또는 근거 있는 유지가 기능·탐색·후보·작업에 반영되게 한다 (§§27.11–27.12).

### 7.2 Multi-Frame Generator

**목적:** 최초 접근법과 다른 지식 공간·해결 경로를 탐색한다.

```text
Frame = (Object, Representation, Mechanism, Intervention, Evidence)
```

다음 변환 축을 사용한다.

- Abstraction Shift
- Representation Shift
- Mechanism Shift
- Boundary Shift
- Causal Shift
- Optimization Shift

**입력:** 목표, 기존 Frame, 가정, 기능 결핍, 발견한 지식.

**출력:** 새로운 Frame, 기존 Frame과의 차이, 새 정보 요구사항.

새 Frame은 다음 중 의미 있는 변화를 제공해야 한다.

- 정보 요구사항
- 해결 메커니즘
- 기능 관계
- 핵심 가정
- 탐색해야 할 기술 영역

표현만 다르고 같은 요구사항과 메커니즘을 생성하면 중복으로 처리한다.

새 정보 요구사항은 LearningTask와 목적 연결·의존·후속 행동으로 등록한다. Frame에 문구만 남기는 것으로 처리하지 않는다 (§§21–22).

Frame 수를 미리 고정하지 않는다. 추가 Frame이 중요한 사각지대를 드러낼 가능성과 탐색 비용을 비교한다.

생성한 Frame이 유효하지 않으면 다른 변환 축을 사용하거나 기존 Frame의 기능 도출로 복귀한다. 같은 변환을 근거 없이 반복하지 않는다.

### 7.3 Capability Graph

**목적:** 목표 달성에 필요한 기능과 기능 사이의 연결 조건을 표현한다.

**입력:** `GoalSpec`, Frame, 발견된 자산, 관측된 실패.

**출력:** 기능 노드, 관계, 미충족 조건, 대안 경로.

| 관계 | 의미 |
|---|---|
| AND | 함께 충족해야 하는 기능 묶음 |
| OR | 동일한 목적을 충족하는 대안 |
| REQUIRES | 선행 기능·조건 |
| PROVIDES | 자산이 제공하는 기능 |
| TRANSFORMS | 입력을 출력으로 변환 |
| CONFLICTS | 양립할 수 없는 조건 |
| ENABLES | 다른 기능이나 활용 가능성을 열어 주는 관계 |

AND·OR와 다중 입력은 그룹 단위로 표현한다. 단순한 두 노드 연결만으로 결합 조건이 충족됐다고 간주하지 않는다.

다음 상황에서 기능 분해를 확장한다.

- 수행 방법이 발견되지 않음
- 입력·출력·선행 조건이 불명확함
- 서로 다른 기술적 역할이 하나의 기능에 섞여 있음
- 실패 원인이 현재 분해 수준에서 구분되지 않음

추가 분해가 후보 선택이나 실행 가능성 판단에 영향을 주지 않는다는 근거가 있으면 해당 분해를 중단한다. 영향 미확인을 영향 없음으로 바꾸지 않는다. 그래프는 답변 작성 항목이 아니라 원래 목표에 필요한 기능·조건을 표현한다 (§§21.2·24.6).

AI가 도출한 기능은 추론된 요구사항으로 표시한다. 그것을 사용자 요구사항처럼 승격하거나, 원래의 필수 조건을 임의로 제거하지 않는다. 도구 이름보다 필요한 결과·입출력·소비자·상태·수행 주체를 먼저 정의하고, 기존 능력의 충족 범위와 연결 공백을 판별할 수 있게 구체화한다 (§27.7.6).

### 7.4 Knowledge Discovery와 Deepening

**목적:** 필요한 자산을 발견하고, 선택·조합·적용에 필요한 깊이까지 이해한다.

지식 자산에는 개념·이론·방법론·알고리즘·skill·prompt·라이브러리·CLI·MCP·API를 포함한다.

탐색은 양방향으로 수행한다.

- **Top-down:** 미충족 기능에서 필요한 지식과 자산을 역추적한다.
- **Bottom-up:** 발견한 자산의 능력에서 새로운 기능과 해결 경로를 도출한다.

**입력:** 기능 결핍, 불확실성, 가정, 자산, 근거, 목표·기능에서 발동한 신규 탐색 의무. 현재 후보의 부족함이 없어도 적용 대상에서는 기존 후보 밖을 실제 조사한다 (§§27.8–27.10).

**출력:** `KnowledgeAsset`, `EvidenceRecord`, `LearningTask`의 답·이해·후속 탐색 평가, 새로운 기능·Frame 제안, 상향 반영 의무.

학습은 현재 질문에 답하는 동시에 다음 탐색 공간을 생성한다. 매 결과에서 관측한 새 대상의 역할·필요 이해를 평가하고 필요한 후속 질문을 실제 수행한다. 자식에서도 같은 규칙을 적용하며 결과를 부모·후보·원래 목표까지 반영한다 (§§21–24).

#### K0–K4

| 수준 | 해당 사용 맥락에서의 의미 |
|---|---|
| K0 | 관련 자산의 존재를 인식하지 못함 |
| K1 | 존재와 목적을 파악함 |
| K2 | 기본 원리와 주요 능력을 이해함 |
| K3 | 적용 조건·제약·실패 가능성·호환성을 판단할 수 있음 |
| K4 | 현재 작업에 적용하고 결과를 검증할 수 있을 만큼 이해함 |

K0는 시스템이 모든 미지의 자산을 열거할 수 있다는 뜻이 아니다. 새로운 자산을 발견했을 때 이전 인식 상태와 지식 공백을 표현하는 수준이다.

지식 수준은 기술 전체에 대한 보편적 숙련도가 아니라 **특정 작업·환경·버전에 대한 이해 상태**다.

#### 목표 깊이의 자율 결정

다음 질문 중 현재 의사결정에 영향을 주는 질문이 해결되지 않았다면 심화한다.

- 이 자산을 채택할 수 있는가?
- 필요한 기능을 실제로 제공하는가?
- 다른 요소와 연결할 수 있는가?
- 중요한 실패 조건은 무엇인가?
- 현재 환경에 적용할 수 있는가?
- 적용 결과를 어떻게 확인하는가?
- 새 지식이 기존 문제 표현을 바꾸는가?

현재 단위의 판단과 적용에 충분한 근거가 확보되면 해당 단위의 심화를 끝낼 의무가 있다 (§23). 현재 답에 필수적인 후속 공백은 먼저 해결하고, 독립 후속 질문은 별도 상태로 관리한다. 특정 경로의 정체나 자원 중단을 충분 이해로 기록하지 않는다.

모든 기술을 K4까지 조사하지 않으며, 중요한 기술을 이름만 아는 상태로 채택하지 않는다.

각 심화 결정에는 해결할 질문, 부모 판단에서의 역할, 현재 공백, 필요한 능력·근거, 다음 판별 관측, 종료·재개 조건을 기록한다. K는 이 평가의 요약이며 라벨만으로 이해를 인정하지 않는다. 학습의 입출력과 상태는 §21, 계속 의무는 §22, 종료 의무는 §23을 따른다. 개념 심화·기능 도출부터의 기존 자동화 수단 우선 검토·발견한 자산의 심화와 실제 후속 수행은 §§27.6.7–27.6.14 및 §§27.7.7–27.7.15의 상세 조건에 연결한다.

### 7.5 Composition Search

**목적:** 자산을 연결하여 실행 가능한 해결책 후보를 구성한다.

**입력:** 기능 그래프, 자산, 근거, Frame, 제약.

**출력:** 후보 그래프, 연결 조건, 충족 기능, 결핍, 비교 결과. 기존·신규 후보의 단독·대체·보완·혼합 가능성을 함께 판단하고, 후보 편입 이전의 관련성 판단과 제외·보류에도 역할·범위·근거를 연결한다 (§§27.8–27.10).

필요 조건을 충족하는 후보 사이에서는 기존 자동화 수단의 조합, 사용자에게 남는 개입, 실제 추가 구현·연결 부담과 검증·복구를 비교한다. 개별 자산의 유용성만으로 연결 가능성을 인정하지 않는다 (§§27.7.10–27.7.12·27.7.16–27.7.17).

선택한 각 중요한 구성의 역할과 추가 기여를 단독·더 간단한 관련 조합의 충족 범위와 대조한다. 필수 구성·조건부 추가·대안을 구분하고, 등급·옵션과 추천의 확신도 실제 요구와 근거 범위에 연결한다 (§27.15). 도구 수가 적다는 사실만으로 품질·검증·복구의 기여를 제거하지 않는다.

탐색 전략은 **Capability-Guided Diverse Graph Search**로 유지한다.

| 구성 | 책임 |
|---|---|
| AND/OR Constraint Search | 필수 기능과 대안 경로 검사 |
| Diversity-Preserved Beam Search | 실질적으로 다른 후보 보존 |
| Progressive Widening | 가치 있는 탐색 영역 확장 |
| Pareto-based Selection | 품질·비용·복잡성의 비교 |
| Cross-Frame Composition | 서로 다른 Frame의 자산 결합 |

이는 SynFrame의 복합 전략 명칭이며, 검증된 단일 알고리즘이라는 주장을 하지 않는다.

#### 후보 유지 정책

후보가 들어오면 다음을 평가한다.

1. 미충족 필수 기능을 해결하는가?
2. 기존 후보와 다른 유효한 경로를 제공하는가?
3. 중요한 불확실성을 줄이는가?
4. 연결 조건과 적용 근거가 있는가?
5. 비교 가능한 속성에서 다른 후보에 의해 지배되는가?
6. 유지·검증·확장 비용에 상응하는 기여가 있는가?

결과는 유지·병합·보관·제외 중 하나로 반영한다. 보유 여부나 발견 시점 자체를 품질·적합성의 근거로 삼지 않는다. 단독 부적합을 보완 역할의 부적합으로 확대하지 않으며, 중요한 미확인은 필요한 관측과 실제 후속 작업에 연결한다 (§§27.8–27.10).

확인되지 않은 속성을 임의의 점수로 채워 Pareto 우열을 선언하지 않는다. 후보 간 불확실성이 중요하면 비교에 필요한 정보를 먼저 확보한다.

충분히 탐색하지 않은 Frame을 초기 점수가 낮다는 이유만으로 모두 제거하지 않는다. 보호할 이유와 다음 검증 행동을 함께 정의하며 무기한 보존하지 않는다.

Beam Width는 유지된 후보 집합의 결과로 결정된다. 고정된 후보 수를 먼저 정하고 근거 있는 대안을 잘라내지 않는다.

## 8. Reframe Engine

### 8.1 목적

문제 표현의 가정·대상·메커니즘을 바꾸어 새로운 정보와 해결 경로를 탐색한다.

도구 하나를 다른 도구로 교체하는 것만으로 Reframe이라 부르지 않는다.

### 8.2 정확한 트리거

| 유형 | 발동 조건 |
|---|---|
| Initial | 초기 표현에 중요한 가정이나 사각지대가 있어 다른 접근을 탐색할 필요가 있음 |
| Discovery | 새 지식이 기존 가정을 변경하거나 다른 해결 메커니즘을 제시함 |
| Deficiency | 현재 구조에서 중요한 기능을 충족할 경로가 부족함 |
| Stagnation | 같은 탐색 방향에서 핵심 결핍·불확실성이 개선되지 않고 추가 탐색의 근거가 약해짐 |

정기 실행이나 고정된 횟수 도달을 다섯 번째 트리거로 추가하지 않는다.

Initial은 초기 Multi-Frame 생성과 같은 필요를 공유할 수 있다. 하나의 관측을 근거로 동일한 Frame을 중복 생성하지 않는다.

### 8.3 단계

```text
트리거와 관측 근거 확인
→ 현재 Frame의 핵심 가정 분석
→ 변경할 축 선택
→ 새로운 Frame 생성
→ 구조적 차이 검사
→ 새로운 정보 요구사항 도출
→ Capability Graph 갱신
→ 변경된 가정에 의존하는 판단 식별
→ 해당 판단·후보의 유효성 갱신
→ 관련 범위 재탐색
→ Meta-Controller 복귀
```

각 단계의 결과를 저장 가능한 객체로 연결한다.

새 Frame이 실질적인 차이를 제공하지 않으면 채택하지 않고 다른 축을 검토하거나 기존 탐색으로 복귀한다.

### 8.4 비순환성과 보존

Reframe 전에 더 좋은 해결책이 존재한다는 사실을 알아야 할 필요는 없다.

다만 발동 근거와 변경한 문제 표현은 설명할 수 있어야 한다.

Reframe 이후에는 변경된 가정에 의존하는 결론만 재검토 대상으로 표시한다. 관련 없는 관측·출처·지식은 보존한다.

이전 관측 자체와 그 관측에 대한 해석도 구분한다. 해석이 무효화되었다는 이유로 원래의 관측 기록을 삭제하지 않는다.

## 9. Meta-Controller

### 9.1 책임

하나의 호스트 에이전트가 공통 상태를 관측하며 다음 연산을 선택한다.

```text
GENERATE_FRAME
DERIVE_CAPABILITY
DISCOVER_KNOWLEDGE
DEEPEN_KNOWLEDGE
EXPAND_COMPOSITION
REVIEW_SOLUTION
REFRAME
SIMPLIFY
COMMIT
```

Goal Compiler와 실행 관리 명령은 이 연산 집합을 준비·유지하는 별도 책임이다.

외부 도구 사용과 실제 구현은 선택한 연산 또는 채택된 해결책의 실행 작업에 연결한다.

### 9.2 행동 선택 정책

| 우선 판단 | 처리 |
|---|---|
| Feasibility | 권한·자원·전제 조건상 불가능한 행동 제외 |
| Consistency | 무효화된 근거와 상태 충돌 처리 우선 |
| Critical Gaps | 필수 기능·의존성 결핍 해결 |
| Decision Uncertainty | 중요한 선택을 막는 불확실성 해소 |
| Discovery Value | 새로운 경로를 열 수 있는 탐색 검토 |
| Marginal Cost | 기대 기여와 비용 비교 |
| Commit Readiness | 채택 조건과 종료 근거 확인 |

이는 고정 파이프라인이 아니라 경쟁하는 행동의 우선순위 정책이다. 처리해야 할 의무와 수행 순서를 구분한다. 후속 질문·상향 반영·종료 판정이 실제 후보 행동과 채택 가능성을 변경해야 한다 (§25). 자동화 우선 검토는 이 정책 안에서 기능 도출부터 기존 수단과 조합을 평가하는 의무다. 권한·일관성·중요 실패의 처리를 밀어내지 않으며, 저렴한 직접 작업이 있다는 이유로 중요한 평가 의무를 삭제하지 않는다 (§27.7.13).

동일한 결핍을 해결할 수 있는 행동이 여러 개라면 다음을 비교한다.

- 현재 근거에 직접 연결되는가?
- 중요한 의존성을 더 많이 해소하는가?
- 검증 가능한 결과를 제공하는가?
- 더 적은 비용으로 같은 판단을 개선하는가?
- 실패 시 다른 경로로 전환하기 쉬운가?

명확한 우열이 없으면 판단을 바꿀 수 있는 정보를 가장 적은 비용으로 확보하는 행동을 선택한다. 적용 대상의 신규 탐색·통합 조합은 별도 필수 의무다. 가치·비용 비교는 수행 순서와 유한한 탐색 종료에 사용하며, 아직 수행하지 않은 의무의 취소 근거로 사용하지 않는다 (§§27.8–27.10).

### 9.3 추가 탐색의 가치

```text
Value(action) = DecisionImprovement(action) − ExecutionCost(action)
```

Decision Improvement는 결핍 해소, 불확실성 감소, 새 경로 확보, 조합 품질 개선을 포함한다.

이 식은 근거 없는 수치 계산을 강제하지 않는다. 정량 근거가 없으면 상대 평가와 관측 이유를 사용한다. 평가할 실제 공백·관측 경로·행동 대안과 의무 보존은 §§27.6.5–27.6.11·27.6.17을 함께 적용한다.

### 9.4 정체 판단

다음을 함께 검토한다.

- 같은 중요한 결핍이 남아 있음
- 결과가 기존 자산과 중복됨
- 후보 추가가 기능 충족을 개선하지 못함
- 중요한 불확실성이 줄어들지 않음
- 같은 방향의 추가 탐색을 정당화할 근거가 약함

한 경로의 정체를 전체 탐색 공간의 소진으로 간주하지 않는다. 다른 정보원·추상화 수준·Frame에서 진전 가능성이 있으면 전환한다.

## 10. Review·Simplify·Commit·Execution

### 10.1 Review

후보를 원문 목표·현재 성공 기준·정확한 상태 버전에 대조한다. 중요한 후속 발견·보류 질문·상향 미반영·조건부 충돌·선택 비교의 유효성을 포함한 입력과 판정은 §25.3을 따른다.

검토 대상은 다음과 같다.

- 필수 기능 충족
- 입력·출력·의존성 연결
- 자산의 실제 적용 조건
- 근거의 출처·유효 범위
- 중요한 충돌과 실패 가능성
- 불필요한 복잡성
- 현재 후보를 선택할 이유
- 추가 조사로 판단이 바뀔 가능성

결함이 발견되면 해당 결함을 기능·지식·조합·Frame 문제로 분류하여 실제 후속 질문·연산으로 등록하고 컨트롤러로 돌려보낸다. 검토 양식 작성만으로 결함이 해소된 것으로 처리하지 않는다. 원문 목적·필요 능력·중요성 미확인·상향 미반영·추가 탐색 대안의 상세 대조와 판정별 행동은 §27.6.17을 따른다. 자동화 평가 누락, 중요한 연결 미확인, 근거 없는 새 구현·수동 보완, 새 지식의 작업 의무 미반영은 §27.7.19에 따라 대조하고 필요한 실제 후속 작업에 연결한다.

§27.15의 추가 구성 필요성·등급·옵션·추천 근거 범위도 현재 후보의 복잡성·선택 이유·주장 유효성으로 검토한다. 후보 안의 비교 근거가 최종 기본 추천과 조건부 안내에 실제로 반영되는지 대조한다.

### 10.2 Simplify

불필요한 요소와 중복 단계를 제거하되 다음을 보존한다.

- 필수 기능
- 중요한 대안 경로
- 검증과 복구 능력
- 유효한 근거와 출처
- 명시적 제약

단순화로 후보가 변경되면 새 버전으로 저장하고 영향받는 검증을 다시 수행한다. 변경 전 검증을 그대로 재사용하지 않는다.

§27.15에 따라 불필요한 구성·등급·연결을 제거하거나 조건부로 옮길 때에도 원문 조건·중요 품질·검증·복구와 실제 후속 작업의 보존을 대조한다. 최종 안내만 줄이고 현재 후보와 작업 의무를 그대로 남기지 않는다.

### 10.3 Commit

다음 조건을 모두 충족해야 한다.

1. 필수 기능을 충족하는 실행 가능한 조합이 존재한다.
2. 중요한 입력·출력·의존 관계가 연결되어 있다.
3. 적용에 필요한 지식과 근거가 확보되어 있다.
4. 중요한 근거 충돌과 구조적 결핍이 해결되어 있다.
5. 추가 탐색이 의사결정을 실질적으로 개선할 근거가 부족하다.
6. 현재 후보와 의존 객체의 정확한 버전에 대한 채택 자격 검사가 통과했다.

의미적 조건은 호스트 에이전트가 근거와 함께 평가한다. 보조 코드는 구조적 조건, 근거 연결, 검토 기록의 존재·유효성, 버전 일치를 검사한다.

코드가 의미적 주장의 진실을 자동으로 증명한다고 간주하지 않는다. 중요한 정보 공백·미판별 발견·상향 미반영·조건부 충돌·오래된 검토를 차단하는 상세 조건은 §25.4를 따른다.

`COMMIT`은 해결책 채택이며, 사용자가 요구한 모든 외부 작업의 완료와 항상 같은 뜻은 아니다. 적용 판정과 적용되는 두 의무의 존재·현재 참조·실제 충족을 Review의 임의 선언과 별도로 대조한다. 미수행 필수 의무나 현재 선택의 유효성을 막는 공백은 채택을 차단하되, 근거 있게 보류한 독립 개선 질문의 존재만으로 차단하지 않는다 (§27.10).

### 10.4 Execution

실제 구현이나 산출물 생성이 요청된 경우 채택된 해결책을 실행한다.

실행 전에는 해당 작업의 권한·전제·입력·검증 방법을 확인하고, 실행 후에는 관측된 결과를 저장한다.

실행에서 새로운 결핍이나 잘못된 가정이 발견되면 해당 근거를 컨트롤러에 반환한다. 필요한 범위의 후보 수정·지식 심화·Reframe을 수행한다.

실행 결과를 확인하지 못했다면 확인하지 못한 것으로 표시한다. 설계상 가능하다는 판단을 실제 실행 성공으로 바꾸어 기록하지 않는다.

## 15. 자원 배분과 종료 제어

### 15.1 동적 배분

다음을 관측한다.

- 기능·의존성의 규모
- 중요한 불확실성
- Frame과 후보의 다양성
- 잘못된 판단의 영향
- 현재 해결책의 완성도
- 최근 탐색의 실제 기여
- 시간·검색·도구 실행 비용
- 확인 가능한 자원 한도

호스트가 제공하지 않는 잔여 토큰이나 비용은 `unknown`으로 취급한다.

관측 불가능하다는 이유로 탐색을 무제한 지속하지 않는다. 확인 가능한 시간·기여·결핍·중복·실행 제약으로 계속할 근거를 판단한다.

### 15.2 총량과 배분의 구분

사용자나 호스트가 정한 자원 한도는 준수한다.

그 한도 안에서 어떤 기능·Frame·불확실성에 자원을 배분할지는 Meta-Controller가 결정한다.

Frame 수, Beam Width, 검색 횟수, K 수준, 정체 횟수에 임의의 고정값을 도입하지 않는다.

### 15.3 종료 분류

- 성공 조건 충족: `COMPLETED`
- 필수 조건이 남고 유효한 부분 결과를 반환: `PARTIAL`
- 실제 외부 조건 해소가 필요: `BLOCKED`
- 재개를 위한 중단: `SUSPENDED`
- 복구할 수 없는 실행 오류: `FAILED`
- 사용자 취소: `CANCELLED`

추가 탐색의 한계효용이 낮다는 판단은 세계 전체의 최적해를 증명했다는 뜻이 아니다.

필수 기능을 충족하지 못한 상태에서 자원만 소진되었다면 완료로 처리하지 않는다.

## 18. 실패 모드와 대응

| 상황 | 대응 |
|---|---|
| 유효한 Frame이 생성되지 않음 | 변환 축 변경 또는 기존 Frame에서 기능 도출 |
| 관련 지식을 찾지 못함 | 검색 표현·정보원·추상화 수준 변경 |
| 자산의 근거 부족 | 영향에 따라 조사·보류·대안 탐색 |
| 자산을 실행할 수 없음 | 실제 사용 가능성과 대체 경로 확인 |
| 조합의 입출력·전제가 맞지 않음 | 변환 계층 또는 대체 조합 탐색 |
| 후보가 중복됨 | 병합·보관하고 다른 경로 탐색 |
| 새 지식이 가정을 바꿈 | 의존 상태 무효화 및 Discovery Reframe |
| 중요한 기능을 해결할 경로가 없음 | Deficiency Reframe 검토 |
| 같은 탐색에서 진전이 없음 | Stagnation 판단 후 경로 전환 |
| 참고 계약을 읽지 않은 상태 | 해당 연산 전에 필수 계약 로딩 |
| 상태 저장 실패 | 저장 성공을 주장하지 않고 오류 복구·실행 범위 재평가 |
| 도구 결과 적용 전 중단 | 실제 결과와 저장 상태 대조 후 재사용 또는 복구 |
| 외부 변경 여부 불명확 | 상태 확인 후 재시도 여부 결정 |
| 컨텍스트 손실 | 계약과 체크포인트를 복원 |
| 계약·스키마 버전 불일치 | 호환성 확인 또는 검증된 마이그레이션 |
| 필수 조건 미충족·자원 소진 | `PARTIAL` |
| 외부 조건 없이는 진행 불가 | 대체 경로 확인 후 `BLOCKED` |

동일한 입력·환경·전제에서 실패한 작업을 새 근거 없이 반복하지 않는다.

일시적 장애의 해소나 입력·환경 변경은 재시도 근거가 될 수 있다. 단순히 “다시 해보자”는 이유만으로 반복하지 않는다.
