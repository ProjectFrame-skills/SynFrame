# 채택된 v3.2 운영 계약

채택된 합의 원문의 담당 절을 생략 없이 배포한다. §§21–27.17는 선택적 부록이 아니라 현재 실행 계약이다. 의미 판단은 단일 호스트, 상태·참조·검증은 코어의 책임이다.

## 11. 결정론적 코드와 AI 판단의 경계

| 기능 | 담당 |
|---|---|
| 목표의 의미 해석 | 호스트 에이전트 |
| Frame 생성과 구조적 차이 해석 | 호스트 에이전트 |
| 관련 지식과 조사 방향 발견 | 호스트 에이전트 |
| 상호보완성·적용 가능성 판단 | 호스트 에이전트 + 외부 근거 |
| 경쟁 후보의 의미적 비교 | 호스트 에이전트 + 근거 |
| 스키마·참조 무결성 검사 | 보조 코드 |
| 구조화된 명시적 제약 검사 | 보조 코드 |
| AND/OR·선행 조건 계산 | 보조 코드 |
| 명시된 비교 속성의 계산 | 보조 코드 |
| 상태 버전·무효화 전파 | 보조 코드 |
| 트랜잭션·중복 적용 방지 | 보조 코드 |
| 체크포인트 생성·복원 | 보조 코드 |
| Commit 자격의 구조적 검사 | 보조 코드 |
| 실제 도구의 권한 통제 | 호스트 실행 환경 |

보조 코드가 담당하는 기능을 지침 문구만으로 구현했다고 주장하지 않는다.

또한 skill은 호스트 에이전트의 모든 행동을 강제로 가로채는 실행 관리자라고 가정하지 않는다.

보조 코드는 자신이 관리하는 상태에 대해 불변식을 강제한다. 에이전트가 필수 검증을 생략하거나 기록과 다른 완료 주장을 하는 문제는 행동 평가와 실행 기록 대조로 검출한다.

## 12. 상태·엔터티·관계

### 12.1 공통 메타데이터

주요 객체에는 다음을 포함한다.

```text
id
schema_version
created_at
updated_at
source_run_id
provenance
validity_status
revision
```

### 12.2 필수 엔터티

| 엔터티 | 필수 정보 |
|---|---|
| GoalSpec | 목표, 결과 유형, 성공 기준, 명시적 제약, 추론된 요구사항, 원문 연결 |
| Frame | O/R/M/I/E, 가정, 부모·변환 이력, 구조적 차이, 정보 요구사항 |
| Capability | 기능, 입출력, 충족 조건, 필수 여부와 도출 근거 |
| KnowledgeAsset | 종류, 식별·버전, 제공 기능, 적용 조건, 사용 맥락별 K 수준 |
| EvidenceRecord | 주장, 출처, 관측·확인 시점, 환경, 검증 상태, 유효 범위 |
| SolutionCandidate | 구성 자산, 연결, 충족 기능, 결핍, 비용·품질 속성, 비교 근거 |
| DecisionRecord | DDC, 선택 행동, 주요 대안, 근거, 참조한 상태 버전, 결과 |
| ReasoningRun | run_id, 목표 버전, 상태, 계약 버전, 환경, 자원 관측 |
| Checkpoint | 복원 가능한 상태 버전, 미완료 작업, 참조 파일 |
| DependencyLink | 의존 객체·버전, 관계 종류, 근거, AND/OR 그룹 |
| OperationRecord | 연산, 입력 참조, 실행 의도, 시도, 결과, 적용 여부, 멱등 키 |
| ReviewRecord | 검토 후보 버전, 검사 결과, 의미적 판단 근거, 미해결 사항 |
| SolutionPackage | 채택 후보, 출력 항목, 완료 범위, 산출물·검증 참조 |
| LearningTask | 질문, 목적·부모 연결, 필요한 이해, 답·근거·후속 발견, 작업·처리 상태, 종료·재개 조건 |

v3.1의 13개 엔터티를 보존하고 LearningTask를 추가하여 14개로 한다. 필드·상태 축은 §21, 관계·반영 의무는 §24를 따른다. 반영 의무와 주장 항목은 버전 있는 소유 객체 내 안정적인 ID로 관리할 수 있다.

### 12.3 관계와 불변식

- 자산과 자산에 대한 주장은 별도 객체다.
- 기능 충족에는 자산 연결과 근거가 필요하다.
- 후보는 사용한 자산·가정·근거의 버전에 의존한다.
- 결정은 판단 시점의 상태를 참조한다.
- 검토는 정확한 후보 버전에 적용된다.
- 변경된 가정·근거에서 의존 방향을 따라 무효화한다.
- 무효화된 근거에 의존하는 후보를 검토 없이 채택하지 않는다.
- OR 관계는 유효한 대안 경로로, AND 관계는 필요한 전체 구성으로 평가한다.
- 단순한 순환 참조를 기능 충족의 증거로 인정하지 않는다.
- 원본 관측과 과거 결정은 삭제 대신 이력과 유효 상태로 보존한다.

### 12.4 저장

SQLite를 기본 영속 저장소로 유지한다.

중요한 상태 변경과 연산 결과 적용은 트랜잭션으로 처리한다. 보조 코드를 통한 상태 변경에는 스키마·참조·버전 검사를 적용한다.

하나의 실행에 대한 충돌하는 쓰기는 직렬화하거나 거부한다. 오래된 상태 버전을 기준으로 생성된 결과는 현재 상태와 대조한 뒤 적용한다.

큰 산출물은 파일로 보관할 수 있으며, 저장소에는 실제 경로·버전 또는 해시·출처를 연결한다.

## 13. 실행 상태와 복구

### 13.1 실행 상태

| 상태 | 의미 |
|---|---|
| CREATED | 목표와 실행 식별자가 등록됨 |
| ACTIVE | 호스트 에이전트가 작업을 수행 중 |
| SUSPENDED | 중단되어 재개를 기다림 |
| BLOCKED | 필요한 접근·정보·자원이 없고 유효한 대체 경로도 없음 |
| COMPLETED | 해당 실행의 성공 조건과 검증을 충족함 |
| PARTIAL | 유효한 부분 결과가 있으나 필수 조건이 남음 |
| FAILED | 실행 오류 등으로 유효한 복구 경로 없이 종료됨 |
| CANCELLED | 명시적으로 취소됨 |

`CHECKPOINTED`는 실행 상태로 사용하지 않는다. `checkpoint_version`과 저장 성공 시점으로 관리한다.

### 13.2 전이 원칙

```text
CREATED → ACTIVE

ACTIVE → COMPLETED / PARTIAL / FAILED / CANCELLED
ACTIVE → SUSPENDED / BLOCKED

SUSPENDED → ACTIVE
BLOCKED → ACTIVE
```

재개 시에는 원인이 해소되었는지 확인한다.

이미 종료된 실행에 새로운 목표를 덮어쓰지 않는다. 새로운 실행이나 명시적 후속 버전을 생성하고 이전 결과를 연결한다.

비정상 종료로 저장된 상태가 `ACTIVE`에 머물 수 있다. 재개 시 실제 작업의 생존 여부와 미완료 연산을 확인하며 자동으로 완료나 실패를 추정하지 않는다.

### 13.3 기록 가능한 경계

Skill이 관리하는 명시적 연산과 외부 작업에 대해 다음을 기록한다.

```text
입력·참조 버전·실행 의도 저장
→ 실행
→ 관측한 결과 저장
→ 상태 반영
→ 체크포인트
```

호스트 내부의 모든 모델 호출이나 비공개 추론을 관측·기록한다고 약속하지 않는다.

중단 직전 저장되지 않은 판단은 유실될 수 있다. 복구는 마지막으로 저장된 유효 상태를 기준으로 수행한다.

### 13.4 재개 절차

```text
run_id와 상태 위치 확인
→ 적용 계약 로딩
→ 저장된 목표·그래프·후보·근거·결정 복원
→ 계약·스키마 버전 호환성 확인
→ 미완료 연산과 외부 부작용 확인
→ 완료된 결과 재사용
→ 필요한 범위만 복구
→ ACTIVE로 전환하여 계속 수행
```

외부 작업의 성공 여부가 불명확하면 먼저 확인한다. 같은 외부 변경을 무조건 다시 실행하지 않는다.

멱등 키는 저장된 결과의 중복 적용을 방지한다. 외부 서비스가 멱등성을 지원하지 않는 경우까지 정확히 한 번 실행을 보장한다고 주장하지 않는다.

### 13.5 실행 수명

SynFrame skill만으로 호스트 종료 후 백그라운드 실행이나 자동 재시작을 보장하지 않는다.

현재 실행 중에는 자율적으로 진행하고, 중단 후에는 명시적으로 호출된 재개 절차에서 계속한다.

별도 예약 실행 기능은 호스트가 실제로 제공하고 해당 사용이 요청된 경우에만 연결한다. 기본 구조의 필수 구성으로 두지 않는다.

## 14. 작업 모드와 실행 알고리즘

### 14.1 작업 모드

기존 여섯 인터페이스의 책임을 보존한다.

| 모드 | 책임 |
|---|---|
| solve | 목표 등록 후 자율적 문제 해결 시작 |
| status | 저장된 실행 상태와 미해결 조건 조회 |
| resume | 저장된 실행을 복원하여 계속 수행 |
| result | 해결책·산출물·검증 결과 조회 |
| explain | 주요 선택·조합·Reframe의 근거 조회 |
| cancel | 실행 취소 기록 및 가능한 중단 처리 |

이는 MCP 엔드포인트가 아니라 skill이 지원하는 작업 모드다.

보조 코드의 명령은 상태 생성·조회·검증·저장·복구를 수행한다. `solve` 명령 하나가 독립적으로 LLM을 실행한다고 가정하지 않는다.

호스트 에이전트가 작업 모드를 해석하고 필요한 보조 명령과 도구를 사용한다.

취소는 이후 작업을 중지하는 책임이며 이미 발생한 외부 변경을 자동으로 되돌리는 명령이 아니다. 되돌리기는 별도 실행 가능성과 권한을 확인한다.

### 14.2 공통 연산 계약

각 연산은 다음 정보를 교환한다.

```text
입력:
  run_id
  action
  observed_revision
  input_refs
  constraints
  evidence_refs

출력:
  operation_id
  result_refs
  proposed_state_changes
  evidence_refs
  unresolved_items
  observed_effects
  next_decision_inputs
```

보조 코드는 결과의 구조와 참조 버전을 검사한다. 호스트 에이전트는 의미적 결과를 생성하고 해석한다.

### 14.3 의사코드

```text
신규 생성 또는 복원 → 원문 목표 보존 → 현재 상태 관측
→ 계속·종료 의무를 포함한 가능 행동 도출 → DDC로 선택
→ 실행 의도 저장 → 실제 연산·관측 → 필요한 의미 평가
→ 결과·후속 질문·상향 의무·무효화의 원자적 적용 → 체크포인트
→ 새 상태로 다음 판단 또는 정확한 채택·실행·종료 분류
```

실제 호출 순서·입출력·중단 처리의 상세 의사코드는 §26.2를 따른다.

이 의사코드는 독립 실행 서버가 아니라 **호스트 판단과 보조 코드 호출 사이의 계약**을 표현한다.

예상 가능한 중단 시에는 저장과 상태 분류를 수행한다. 갑작스러운 종료에서는 마지막 체크포인트 이후의 작업을 재개 절차로 확인한다.
